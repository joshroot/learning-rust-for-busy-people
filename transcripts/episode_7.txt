So, I’m gonna try this new approach and see how it works out.

With that in mind, let’s jump back into the "minised" codebase. In the last episode, I provided an overview of the "sed" command-line utility and the scope of features that we’ll include in our "minised" program. I also talked about how to define and instantiate a "struct" in Rust, how to use the "Option" enum, and how to use the "unwrap_or_else" method on a "Result" enum. Today I’ll build on these concepts and continue talking about the other parts of the "minised" codebase.

Previously, I mentioned that two "structs" are defined and used in the codebase, which are the "Config" struct (with a capital "C") and the "Substitution" struct (with a capital "S"). I explained part of the code related to the "Config" struct – specifically, how to define it, how to use  an "impl" block (where "impl" stands for "implementation") to define a constructor function called "build" that is associated with the "Config" struct, how to call this function from inside the binary crate, and how to use the "unwrap_or_else" method for the "Result" enum that’s returned by the "build" function.

I intentionally skipped over a description of what happens inside the "build" function, so let’s dive into that now. The whole point of the "build" function that’s associated with the "Config" struct is to parse the command-line argument values, store these values in a new instance of a "Config" struct, and then return this instance of the "Config" struct. The "build" function takes a single parameter, "args", which is a vector of command-line arguments as Strings.

You might be wondering why we named this function "build" instead of "new". There’s a helpful explanation for this in the book "The Rust Programming Language", in the chapter titled "An I/O Project: Building a Command Line Program". Here’s how I think about it. Basically, when we define a new "struct" and an associated constructor function, if it’s possible that the constructor function will fail, then "build" is a preferable name. If the constructor function is guaranteed to return a new instance of the "struct", then naming the function "new" would be more appropriate. This isn’t a hard requirement to my knowledge, but it seems like a general guideline.

In our scenario, it’s possible that there will be problems with the command-line arguments that are passed to the constructor function, such as not enough of them, too many of them, or invalid values. That means that there is no guarantee that the constructor function will return a new instance of the "Config" struct; there might be an error. Therefore, we name the function "build" as opposed to "new". Instead of returning a "Config" struct directly, the "build" function returns a "Result" enum, which itself implies that an error might occur during an operation in the "build" function. Use of the "Result" enum allows us to return a new instance of the "Config" type (contained inside an "Ok" variant) if there are no errors related to the command-line arguments that were passed, and it allows us to return an "Err" variant if there is an error.

The next question is, how do we parse and process the command-line arguments? In Python, I’m accustomed to using an existing library to set up a command-line interface and parse command-line arguments, such as the "argparse" module in the Python Standard Library. In Rust, we also have the option to use an existing library for this functionality. However, based on my current knowledge, the Rust Standard Library does not include advanced command-line parsing functionality. In other words, Rust doesn’t have the equivalent of an "argparse" module in its standard library like Python does. The "env" module in the Rust Standard Library can be used to get the command-line arguments that were passed, but that’s as far as it goes.

That means if we want to leverage existing functionality for parsing command-line arguments, we would need to add an external Rust library as a dependency of our project. In other words, a library that’s outside of the Rust Standard Library. If we decided to go this route, we could find a library on the "Crates.io" website that’s used for setting up a command-line interface and parsing command-line arguments. For the purpose of learning and exploring the capabilities of Rust while developing the "minised" program, I intentionally decided to forego the use of any external libraries and use only the functionality available in the Rust Standard Library. My goal here was to force myself to figure out how to process the command-line arguments myself. I acknowledge that what I came up with is not the most optimal, generalized way to parse command-line arguments, but it served as a useful challenge for me.

For our "minised" program, I decided on three valid scenarios for passing command-line arguments. In a sense, these are like hard-coded scenarios  to some degree because the order of the command-line arguments matters. This is obviously not the most flexible approach, but it was  sufficient for the purposes of the "minised" program.

The first scenario involves passing a single command-line argument when running the program, which is the "s" command script string that contains the original string pattern, the replacement string, and a flag that modifies the behavior of the substitution operation. The second scenario involves passing two command-line arguments, which are the "s" command script string and a file path. And the third scenario involves passing three command-line arguments, which are the "-i" option, the "s" command script string, and the file path.

These three scenarios are handled in the body of the "build" function in the "impl" block for the "Config" struct. In this function, the first two steps are to check for too few command-line arguments and for too many command-line arguments based on the length of the "args" vector. We can get the length of a vector by calling its "l-e-n" method. A length of the "args" vector that is too short or too long causes the "build" function to return early (via use of the "return" keyword) with an "Err" variant of the "Result" enum that contains a static string literal error message. If neither of these conditions are met, we know that a valid number of command-line arguments was passed.

Then we use a "let" statement in combination with "if" and "else" expressions to conditionally parse the command-line argument values based on the number of command-line arguments that were passed. In addition, we use tuples and an approach called "de-structuring" to create and assign values to three variables simultaneously. The three variables are called "in_place", "script", and "file_path", which correspond to the three fields that are needed to instantiate a "Config" struct. The syntax of the "de-structuring" approach in Rust (such as having a tuple of three variable names set equal to a tuple of three values) reminds me of the syntax of an "unpacking assignment" in Python, so this approach seemed familiar to me.

The first line in the "let" statement reads "let", then a tuple of the three variable names, then an "equals" sign. The following lines are indented by one level and contain the three conditional expressions which are "if", "else if", and "else" expressions. These correspond to different numbers of command-line arguments. Each expression evaluates to a single tuple, which consists of a Boolean value, a String value, and an Option enum variant that may contain a String value.

Depending on how many command-line arguments were passed, the "in_place" variable will either be "false" or "true", the "script" command variable will always be a String, and the "file_path" variable will either be "None" (with a capital "N") or "Some" (with a capital "S") with a String value inside.

The "script" and "file_path" values are each obtained by indexing the "args" vector (which contains the command-line arguments as String values). Right after we use square brackets to get the value at a certain index in the vector, we call the "clone" method. By calling the "clone" method on each of these indexed String values, we explicitly create independent copies of these values that are completely separate (from a memory standpoint) from the original values in the "args" vector. Another way to think of the "clone" method is that it creates a "deep copy". The notion of a "deep copy" is a concept I often encountered when using DataFrames in the "pandas" library in Python. The way I think about this is that a "deep copy" is a full, separate copy of some data. This is different than a "shallow copy", which is more like a copy of a reference to some data that’s not necessarily completely independent.

My sense is that use of the "clone" method is not optimal from a memory standpoint since we’re creating a deep copy of data. Since I’m not currently focused on performance and since I’m using this for two individual, small String values, I don’t think it’s a major concern right now. I initially tried using references in this part of the codebase, but I couldn’t get this to work as intended, so using the "clone" method offered me a way around this. I realize this won’t always be a good approach to take, so this is definitely something on my radar for future codebases since I don’t want to be too liberal with "clone" operations.

After the "in_place", "script", and "file_path" variables are assigned values via the "de-structuring" syntax, these are used to create a new instance of a "Config" struct which is then wrapped in an "Ok" variant of the "Result" enum, and this serves as the return value of the "build" function.

Now let’s move on to the "Substitution" struct. The purpose of the "Substitution" struct is to group together the values that relate to a string "substitution" operation, which are the original string pattern, the replacement string, and the flag that modifies the behavior of the substitution operation.

The "Substitution" struct has three fields, which are "pattern" (with type String), "replacement" (with type String), and "flag" (with type Flag). The "String" type is something we’ve already encountered numerous times. The "Flag" type is something new, and the reason it’s new is because it’s a custom "enum" that I manually defined. Just like the "Result" enum and the "Option" enum, the "Flag" enum can have possible variants.

I used the "enum" keyword to define the "Flag" enum as having two possible variants, which are "Global" and "Number", where the "Number" variant can contain a value with type "usize". Side note – thus far, I’ve been using the "usize" type for unsigned integers (as opposed to something like "u32"). I don’t know for sure if this is best practice, so I’ll discuss this in a future episode after I know more.

So what’s the purpose of this custom enum, called "Flag"? Well, the last element in the "s" command script string is a flag that is used to modify the behavior of the substitution operation, and this flag can either be a lowercase letter "g" or an integer, so I needed a custom type that could accommodate both of these possibilities.

There is an "impl" block for the "Substitution" struct, and similar to the "Config" struct, this has a constructor function named "build". It’s possible for the "build" function to fail if there’s a problem with the "s" command script string (such as if the flag is an invalid value or is missing entirely). The "build" function takes a single argument, "script", which is a reference to a String. This String is the raw "s" command script string that consists of a lowercase letter "s", then the original string pattern, then the replacement string, then the flag, with a forward slash in between each of these four elements. In the body of the "build" function, we use the "split" method on the "script" variable to split it on the forward slash characters. Then we call the "collect" method to collect these elements into a vector of "string slice" values, where "&str" is used to denote the "string slice" type. This vector is named "split".

Then we use an "if" expression to check whether the vector "split" has exactly four elements. If not, the "build" function returns early with an "Err" variant of the "Result" enum that contains a static string error message. Next, we define variables named "pattern", "replacement", and "flag" and we parse their values from the "split" vector. We explicitly convert the "pattern" and "replacement" values to "String" values (with a capital "S") since values in the "split" vector have a type of "string slice", not "String" (with a capital "S"). The code that does this conversion reads "String" (with a capital "S"), two colons, "from", and then the "string slice" value in parentheses.

We need to transform the "flag" variable from a "string slice" into the custom "Flag" type (with a capital "F") that we defined. To do so, from within the "build" function, we call another function that is named "parse_flag". The "parse_flag" function is defined outside of and above the "Substitution" struct, so this is not directly associated with this struct. My reasoning behind keeping the "parse_flag" function separate and outside of the struct was to allow for easier unit testing.

The "parse_flag" function takes a string slice as its only argument, which is the raw "flag" value that was parsed from the "s" command script. If this value is a lowercase letter "g" then the function returns the "Global" variant of the "Flag" enum. Otherwise, the function will try to convert the value to an integer. If the flag is an integer and it is greater than zero, then the "parse_flag" function returns the "Number" variant of the "Flag" enum, which contains the flag integer value. If the "flag" value is not a lowercase letter "g", if it’s not an integer, or if it’s an integer that’s not greater than zero, then the function returns an "Err" variant of the "Result" enum that contains a static string error message.

Note that the "parse_flag" function is not marked as "public" since this is only used within the library crate, so there is no "pub" keyword at the beginning of the function definition.

If we jump back into the "build" function, the final step involves using the "pattern", "replacement", and "flag" values to create a new instance of the "Substitution" struct and then wrapping this in an "Ok" variant of the "Result" enum, which is the return value for the function.

Similar to the "Config" struct, the "Substitution" struct (and its associated "build" function in the "impl" block) are both marked as "public" via use of the "pub" keyword. This is because both the "Substitution" struct and its "build" function need to be accessible from the binary crate.

Let’s jump over to the binary crate. We create a variable named "sub" (which is an instance of the "Substitution" struct) with a syntax similar to what was used for the definition of the "config" variable above. We use the double colon syntax to call the "build" function for the "Substitution" struct, then we call the "unwrap_or_else" method to handle the "Result" enum and gracefully exit the program if there’s an error.

The final step in the binary crate is to call the "run" function and pass both the "config" variable and the "sub" variable as arguments. The "run" function is defined in the library crate, so now we’ll jump back to that.

In the "run" function, we encounter a new concept called a "match" expression, which is used for control flow. A "match" expression compares a value to a set of patterns and then executes the code affiliated with the matching pattern. This reminds me a bit of a "case" expression or a "switch" expression that I’ve seen in other languages. We’ll use a "match" expression three separate times in the "run" function.

The first time is for getting the contents of the input stream of text (either from standard input or from a file path). We define the variable "contents" to equal the result of the "match" expression, which matches the "file_path" field of the "Config" struct against a value of "None" or "Some", which are the possible variants for the "Option" enum. If this matches to "None", then the input stream of text is read from standard input (by using the "stdin" function in the "io" module and the "read_to_string" function to read the bytes into a mutable String variable named "buffer"). If this matches to the "Some" variant, the input stream of text is read from the file path (by using the "read_to_string" function in the "fs" module). Both of these "read_to_string" functions return a "Result" enum, so we use the question mark operator to propagate errors to the calling code, which means we’d propagate this error to the "main" function in the binary crate, since that’s where the "run" function is called.

The second time we use the "match" expression is to match against the value of the "flag" field in the "Substitution" struct, which is either "Global" or "Number". Basically, in the input stream of text, we need to do either a global replacement of the original string pattern, or we need to do a replacement of the n-th occurrence of the original string pattern in each line. A different function will be called to perform the substitution operation, depending on which variant is matched.

The third time we use the "match" expression is as follows. If the "in_place" field in the "Config" struct is "true" (meaning we’re going to perform an in-place modification of the file), then we’ll match the "file_path" field in the "Config" struct against the "None" and "Some" variants of the "Option" enum. If the "file_path" exists (in other words, it matches against the "Some" variant), then we’ll overwrite the existing file contents with the modified contents. To do this, we use the "write" function in the "fs" module. This function returns a "Result" enum (which means it could fail), so we use the question mark operator to propagate the error to the calling code.

I defined three functions to handle the replacement of the original string pattern in the input stream of text. Here, I’ll focus on what the functions do from a high-level standpoint.

First, let’s talk about global replacement of a string. I defined a function called "replace_matches_globally" that takes two arguments. The first is called "contents" (which is the input stream of text) and the second is called "sub" (which is an instance of the "Substitution" struct). The instance of the "Substitution" struct contains both the original string pattern and the replacement string value. In the body of the function, the "replace" method is called on the "contents" variable and the original string pattern and the replacement string values are passed as arguments. This is similar to Python syntax for string replacement operations and seemed fairly straightforward overall from a conceptual standpoint.

Next, let’s talk about replacing the n-th occurrence of a string in each line. For me, this was a more complex task and I did not find built-in functionality in the Rust standard library that would do this explicit task. So, I needed to think through this from scratch, which was a useful and interesting exercise. I used two separate functions to accomplish this. I  first defined a function called "replace_numberth_match_in_single_line" that performs replacements of the n-th occurrence of a string in a single line of text. Then I defined a function called "replace_numberth_matches" that iterates over each line in the input stream of text and calls the first function on each line. The modified versions of each line are all appended into a single string, which ends up as the full, modified version of the original input stream of text.

In the function "replace_numberth_match_in_single_line", the trick was using the "match_indices" method on an individual line of text (which is a "string slice") and then the "collect" method to collect the values into a vector. The "match_indices" method takes one argument, which is the pattern to search for, and it returns information about the starting index of each instance of the pattern in the string slice on which it was called.  Since we know the starting index of each instance of the pattern in the string slice and we know the length of the pattern itself, this means we have the start index and stop index of each instance of the pattern in the string slice, where the string slice is a given line of text. So, I implemented the following logic. If the n-th occurrence of a string pattern exists in the line of text, then split the line of text into three parts, which are the part to the left of the pattern, the pattern itself, and the part to the right of the pattern. Then replace the pattern with the designated replacement string. Then re-assemble the three strings into a single string. If the pattern is not present in the line of text, or if the n-th occurrence is not present (for example, the substitution flag specified replacement of the fourth occurrence of the pattern but there are only three instances of the pattern present), then return the original line of text as-is.

I called the "split_at" method two separate times on the line of text to split at the appropriate indices. Then I used the "format!" macro to re-assemble the three individual string slices into a single string slice, which is then returned by the function. The "format!" macro is similar to the "println!" macro in that you can provide it a format string that includes curly brackets around existing variables to substitute the values of those variables. The difference is that the "format!" macro returns the new string whereas the "println!" macro prints it to standard output.

Speaking of strings, one thing I needed to do somewhat often in this codebase was to convert back and forth between a "String" (with a capital "S") and a "string slice". The "as_str" method can be used to convert a "String" to a "string slice". The "to_string" method can be used to convert a "string slice" to a "String" (with a capital "S"). I anticipate that I’ll be dealing with these conversions fairly often since a "String" and a "string slice" are two distinct types in Rust. This is different than much of the work I’ve done with strings in Python because in Python I’m accustomed to dealing with a single string type.
